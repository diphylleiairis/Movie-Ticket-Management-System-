# Supabase application schema

[V1__movie_ticket_schema.sql](V1__movie_ticket_schema.sql) creates 22 application tables in `movie_app`, plus constraints, indexes, triggers and the backend-only `check_in_ticket` function. This is the initial schema for review; it has not been executed against Supabase. No seed data, provider credentials, Admin passwords, or encryption keys are included.

## Run on Supabase

Open the intended project's SQL Editor, paste the complete migration and run it once on a database that has no `movie_app` schema. The script uses a transaction and never drops existing application tables. Re-running it fails deliberately instead of masking drift. `btree_gist` is required for the Hall scheduling exclusion constraint; the script enables it if absent and includes `extensions` and `public` in the creation search path for existing extension installations.

When Flyway is enabled in Spring Boot, use this same migration as the source of truth. If SQL Editor has already applied V1, explicitly baseline Flyway at version 1 after checking that the schema matches; do not execute V1 again. Flyway is not yet a dependency in `backend/pom.xml`.

Configure JPA with `spring.jpa.properties.hibernate.default_schema=movie_app`, or explicitly map entities to that schema. Keep `ddl-auto=none` (or use `validate` after entities are implemented). PostgreSQL timestamps are `timestamptz`; send instants with an offset and display them in `Asia/Ho_Chi_Minh`.

## Access model

React calls Spring Boot REST endpoints. Spring Boot owns the users, password hashes, social identity links, six-digit email verification, session cookies, and authorization. Supabase Auth and `auth.users` are not used by this schema. Keep `movie_app` outside Supabase Data API exposed schemas. All tables enable RLS without browser policies; `PUBLIC`, `anon`, `authenticated`, and `service_role` receive no application grants from this migration.

The migration owner can use JDBC to inspect or integrate the schema. For a dedicated runtime database role, provision its credentials outside version control, grant `USAGE` on `movie_app`, required table privileges, and `EXECUTE` on `movie_app.check_in_ticket(uuid,text,uuid,uuid,integer)`. Create backend-only RLS policies for that specific trusted role. A regular JDBC role without these policies is denied by RLS. Do not grant the role to `anon` or `authenticated`; application Customer/Admin/Staff roles remain Spring Boot roles. The staff ID passed to SQL must come from the authenticated server principal.

References: [Supabase RLS and grants](https://supabase.com/docs/guides/database/postgres/row-level-security), [Supabase database roles](https://supabase.com/docs/guides/database/postgres/roles), [PostgreSQL range exclusion constraints](https://www.postgresql.org/docs/current/rangetypes.html), [PostgreSQL constraints](https://www.postgresql.org/docs/current/ddl-constraints.html).

## Transactions required in the backend

- Hall setup: assign a predefined layout and materialize its `seats` before creating a Showtime. Populate one `showtime_seats` row per physical seat when creating that Showtime. Any Showtime, including a draft or later removed one, locks the Hall layout permanently.
- Seat hold: use database time for `hold_started_at`; create the Booking and all `booking_seats`, then acquire every requested seat using `SELECT ... FOR UPDATE` in a stable seat-ID order or conditional updates. Roll back the whole transaction if any seat is unavailable. The schema checks ownership and the 1–10 seat limit at commit; it does not implement the hold acquisition endpoint.
- Expiration: a backend worker releases expired holds and ends unconfirmed Bookings together. A timestamp alone does not execute a release. Reconcile PENDING/UNKNOWN with the provider before choosing the final outcome. Retry never extends the hold.
- Payment: use SePay for bank transfers (`TEST` or explicitly configured `LIVE`), PayPal for card tests (`SANDBOX` only), and `FAKE`/`TEST` for deterministic automated scenarios. These are stored separately on every attempt. Verify provider authentication, expected references, amount, currency, environment, state and replay protection in Spring Boot before recording a VERIFIED event. SQL cannot authenticate a provider signature. One active attempt and one idempotency key per attempt are enforced by database constraints.
- Provider prices: `amount`/`currency` preserve the Booking total. V1 proposes SePay VND and PayPal Sandbox USD. Store `provider_amount`, `provider_currency` and an immutable quote (`exchange_rate`, source, time); the rate means provider currency units per Booking currency unit. `provider_amount = round(amount * exchange_rate, 2)`. Do not invent a conversion rate: configure a test rate/source or obtain an authorized quote before creating an attempt. Verify reported amount/currency against the provider values; reversals use the same provider currency. A new retry attempt can have a new quote, while repeated requests for one attempt keep its original quote.
- Provider references: `provider_order_reference` is the payment correlation code/PayPal order ID; `provider_reference` is the final bank transaction/PayPal capture reference. Deduplication includes provider and environment. Map SePay incoming-transfer amount, configured recipient account, correlation code and transaction ID to the attempt. For PayPal, order approval is not captured payment: verify the authoritative completed capture and its order association. Never store PAN or CVV, including test-card values; use provider-hosted fields.
- SePay reversals: bank-transfer monitoring does not imply an automatic refund API. Confirm the actual provider/account capabilities during integration, and retain an auditable pending resolution if a late successful transfer cannot be fulfilled. Never mark a reversal SUCCESS merely because a request row exists.
- Confirmation: write a verified SUCCESS event, stop the active attempt, mark the Booking CONFIRMED, mark all its seats BOOKED and insert its Ticket in one transaction. Deferred constraints require all these records to agree. Late SUCCESS must atomically reacquire all seats only if AVAILABLE; otherwise retain the payment, request a provider reversal and track it in `payment_reversals`.
- Price: V1 uses a single Showtime base price; copy each selected seat's price into `booking_seats`. Booking total equals the sum of those seat prices. Concessions, fees, promotions and seat-specific pricing need their own agreed price model before backend integration; the frontend checkout remains a demo.
- Ticket QR: generate a cryptographically random token on the backend, store its hash for lookup and authenticated encrypted ciphertext for later display, and record `qr_key_version`. Keep encryption keys outside the database. Re-encrypting with a new key preserves the original token and QR hash. Do not log plaintext QR tokens or payment credentials.
- Check-in: Admin must enter nonnegative `check_in_opens_before_minutes` and `check_in_closes_after_minutes` per Cinema, with no universal default. Both offsets use Showtime start: `[starts_at - opening offset, starts_at + closing offset]`, inclusive. Example only: 30/15 allows 18:30–19:15 for a 19:00 Showtime. The authenticated staff workflow previews the QR without consuming anything, then confirms a group through `check_in_ticket`. The function checks the Cinema's current settings using server wall-clock time after acquiring locks, rejects early/late or excess entries, updates the count and writes its log atomically. A retry returns the original result without recounting; a later group uses a new request ID and must still be inside the window.

Provider references: [SePay Test Mode](https://docs.sepay.vn/test-mode.html), [SePay webhook authentication](https://developer.sepay.vn/en/sepay-webhooks/xac-thuc), [PayPal Sandbox](https://developer.paypal.com/sandbox-testing/overview/), [PayPal currency codes](https://developer.paypal.com/api/codes/currency/), [PayPal card testing](https://developer.paypal.com/api/save-with-purchase/test-integration/). Environment credentials, PayPal merchant eligibility, currency setup and provider-specific status/reversal mapping still need configuration during integration.

The migration does not configure scheduled workers, deliver verification email, contact a Payment Provider, implement Spring Security, or expose REST endpoints. Those workflows must use module application contracts and the transaction rules above. All historical foreign keys restrict deletion; Showtime removal is normally `status='REMOVED'`.
